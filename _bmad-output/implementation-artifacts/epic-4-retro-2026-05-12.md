## Successes

1. **Clean progressive architecture** — Each story built cleanly on the previous one (filter → detect → stage → review UI → management UI). No major refactoring was needed between stories, and the data flow from `BlocklistFilterResult` through `LlmEntityDetectionResult` into `StagingQueue` was designed once and worked throughout.

2. **FR28 mandatory gate enforcement** — The hardest requirement ("nothing bypasses the staging queue") was implemented at the service layer, not the controller layer. Both zero-flag and flagged threads are staged identically. `getApprovedThreadIds()` is ready for Epic 5/6 consumption.

3. **Test discipline scaled with complexity** — From 267 tests at Story 4.1 to 393 at epic close. Each story added comprehensive unit tests covering edge cases (regex escaping, word boundaries, per-thread error isolation, discriminated union type narrowing, transaction atomicity).

4. **Code review effectiveness** — Story 4.2 had 8 review follow-ups, all resolved. The DB fallback for blocklist loading, permissive fence stripping, and intra-response entity dedup were real improvements caught by review.

5. **Frontend governance UI delivered** — Complete admin staging review interface with workstream/batch filtering, approve/reject/bulk-approve-clean workflows, batch completion toasts, and blocklist quick-add from flagged entities. All behind `@Roles('ADMIN')` and route guards.

6. **Consistent error isolation** — Per-thread/per-item error isolation pattern used in every processor and service (blocklist filter, LLM entity detector, staging queue, staging review bulk operations, blocklist CRUD). One failure never blocks others.

## Challenges

1. **Infra-gated E2E validation gap** — Stories 4.1, 4.2, and 4.3 all document the same gap: full end-to-end validation requires running PostgreSQL + Keycloak + Ollama, which was not consistently available. Unit test coverage is strong, but the complete `import → classify → summarize → embed → filter → detect → stage → review → approve` chain has not been exercised in a live environment for this epic.

2. **Deferred hardening accumulation** — Story 4.2 alone produced 6 explicit deferrals (substring/alias entity matching, sequential LLM calls at scale, observability gaps, prompt injection surface, E2E parity verification, threadsProcessed semantics). These are real risks for production readiness.

3. **Synchronous pipeline endpoint growing unbounded** — The `POST /api/admin/pipeline/run` endpoint now chains 7 sequential stages. No timeout, no progress reporting, no cancellation. This was flagged as MED debt in Epic 3 retro and has gotten worse.

4. **Story 3.7 merge regression carried through** — The orphaned action detector files lost during the Epic 3 PR merge were cleaned up in Story 4.1, but the regression itself (missing processor integration on `develop`) was noted as a known gap rather than fixed.

5. **Keycloak dependency blocks HTTP-level testing** — Full HTTP-level E2E (authenticated requests through NestJS guards) requires a live Keycloak OIDC endpoint. All stories validated at the service/ORM level but not through the HTTP stack with real JWT tokens.

## Key Insights

1. **Progressive pipeline layering is a proven pattern.** Epic 4 extended the pipeline with 3 new stages without redesigning anything. The processor → service → controller → response chain scales well for new capabilities.

2. **Service-layer gates > middleware gates.** Enforcing the anonymization gate at the service layer (not controller or middleware) means no bypass path exists regardless of how endpoints are added in future epics.

3. **Discriminated unions for flag sources work well.** The `AnonymizationFlag` discriminated union (`BLOCKLIST` | `LLM`) cleanly separates flag sources while keeping them composable. Story 4.2 added `LLM` flags without modifying blocklist filter code.

4. **Review-driven improvement works when the feedback loop is tight.** Story 4.2's 8 review patches were all applied in the same story cycle. The DB fallback pattern and fence regex improvements were real quality gains.

5. **Deferred items need formal triage, not just documentation.** 6 new deferrals from one story is a signal that the "defer and document" pattern needs a periodic sweep. Items older than 2 epics should be triaged per team agreement A8 from Epic 3.
