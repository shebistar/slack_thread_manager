## Successes

1. **Clean 6-story progressive architecture** — Each story built on the prior one without refactoring. 5.1 (backend + DB + cron) → 5.2 (API + Dashboard layout) → 5.3 (Feed layout) → 5.4 (Split Panel) → 5.5 (read state) → 5.6 (API expansion + key factory). The data model was designed once in 5.1 and consumed without changes through 5.6.

2. **Three role-specific layouts from a single API** — One `GET /briefings/today` endpoint serves all three UX variants (Dashboard, News Feed, Split Panel). Role-to-shape mapping decided at generation time means zero frontend branching on data shape — only layout selection.

3. **Reusable component architecture** — `BriefingCard` supports 3 variants (`compact`, `standard`, `featured`), 5 visual states (`unread`, `read`, `selected`, `flagged-quiet`, `expanded`), and 2 interaction modes (`expand/collapse` vs `select`). Built incrementally across 4 stories without breaking backward compatibility.

4. **Code review rigor caught real issues** — 17 review patches across Stories 5.2 and 5.4. Notable catches: JWT `sub` vs email user resolution (5.2), heading hierarchy accessibility violation (5.2), stale `selectedItemId` after data refetch (5.4), `aria-selected` listbox pattern (5.4), CSS class conflicts between `selected` + `gone_quiet` states (5.4).

5. **Text-paste parity maintained across all 6 stories** — Every story independently verified that text-paste-imported content renders identically to Slack API content. This is now a proven product-level guarantee.

6. **TanStack Query patterns matured** — Progressed from a single `BRIEFINGS_KEY` constant (5.2) to optimistic mutations with `setQueryData` (5.5) to a full `briefingKeys` factory (5.6). Cache management is production-ready.

7. **Critical pipeline fixes shipped proactively in 5.1** — Blocklist filter pass-through bug (zero entries blocked entire pipeline), correlation crash isolation, removal of dangerous `drizzle-kit push` fallback, `tablesFilter` safeguard, OpenShift route timeout fix.

## Challenges

1. **Infra-gated E2E validation gap — third consecutive epic** — Same gap documented in Epic 3 and Epic 4 retros. Full HTTP-stack validation with Keycloak authentication was not performed. The 11-step OpenShift smoke test in 5.1 was developer-driven, not QA-gated.

2. **Deferred items never triaged — A8 agreement unexecuted** — Epic 4 retro created action #2 ("triage all deferred items per A8"). It wasn't done. We now carry: 5 items from Epic 1 (4 epics old), 6 from Epic 4, and 3 new from Epic 5 = **14 open deferred items** with no triage process.

3. **UX design direction drift (PROJECT LEAD ESCALATION)** — The original UX design directions (`ux-design-directions.html`) defined distinctive visual treatments for each layout: dark Grafana-style header for Dashboard, red-bordered briefing header for News Feed, role badge topbar for Split Panel. During incremental implementation, these defining elements were flattened into the generic app shell. Each story reused the previous story's layout structure rather than referring back to the original design spec. See "UX Fidelity Audit" section below.

4. **PM role mapping was temporarily wrong** — Story 5.2 mapped PM → Dashboard instead of PM → Feed. Fixed in 5.3, but it means any PM testing against 5.2 would have seen the wrong layout.

5. **Shadcn component assumptions were wrong** — Story 5.2 assumed Card component "already existed." It didn't and had to be created from scratch. Story planning must verify component availability.

6. **drizzle-kit push incident (5.1)** — `drizzle-kit push` dropped all Keycloak tables because they weren't in the Drizzle schema. Required full Keycloak restoration. The fallback was removed and `tablesFilter` safeguard added, but the incident was severe.

7. **Route-level tests still absent** — Three full layout implementations with no integration-level test coverage. Gap carried since Story 5.2 across 4 stories.

8. **Enum style mismatch unresolved** — Zod schemas use `SCREAMING_SNAKE`, API returns `snake_case`. Creates confusion for anyone reading the shared schema types.

### Root Cause

Each story reused the prior story's layout structure instead of cross-referencing `ux-design-directions.html`. The design directions file was not listed in story `### References` sections and was not loaded as a persistent fact by the dev workflow.

## Key Insights

1. **API-first, shape-at-generation-time was the right call.** Storing role-appropriate content at briefing generation means the frontend is purely a rendering layer. This pattern should carry to Epic 6 search results.

2. **Incremental component extension scales.** BriefingCard was touched by 4 stories and grew from 1 to 3 variants + 5 states without breakage. Key: optional props with backward-compatible defaults.

3. **17 code review patches = reviews are working.** Accessibility catches and state management fixes wouldn't have been found without review.

4. **Multi-model epic execution works.** Stories 5.1–5.5 (Opus 4.6) + Story 5.6 (Codex 5.3) — seamless handoff via comprehensive "Existing Code Intelligence" sections. Validates the BMAD story format as a cross-model contract.

5. **Design direction fidelity requires explicit reference loading.** The UX design HTML was produced during brainstorming but not carried into story creation as a mandatory reference. Incremental development naturally flattens distinctive design elements unless the original spec is actively consulted per story.

6. **Infrastructure hardening should be tracked separately.** Story 5.1 delivered ~8 infrastructure fixes hidden inside a "briefing generation" story. These are real deliverables that deserve visibility.
