## Successes

1. **Clean 4-story progressive architecture with zero refactoring** — 6.1 (DB + FTS service) → 6.2 (vector + hybrid merge) → 6.3 (API orchestration) → 6.4 (frontend). SearchModule designed once in 6.1, extended through 6.4 without schema changes or service rewrites.

2. **Multi-model execution worked seamlessly** — Opus 4.6 (6.1, 6.4) and Sonnet 4.6 (6.2, 6.3). BMAD story format with "Existing Code Intelligence" sections proved effective as cross-model handoff contract for second consecutive epic.

3. **FR28 anonymization gate enforced in search** — FTS document built exclusively from `anonymizedContent` (post-staging approval). `primary_topic` deliberately excluded (bypasses anonymization gate). Defense-in-depth: every search query filters `pipeline_state = 'approved'`.

4. **[B2] pgvector HNSW index resolved** — Deferred since Epic 3 Story 3.5. Verified in Story 6.2: index present, `<=>` operator correct, EXPLAIN ANALYZE confirmed.

5. **Deferred item triage honored for the first time** — 7 items resolved on 2026-05-12 including pipeline timeout, `createDb('')` crash, PII logging, role claim default.

6. **Code review caught real issues** — 10 patches. Key catches: AC7 backfill migration gap, approval flow FTS guard, empty document handling, query limit validation, error UI leaking raw payload, whitespace trim, vacuous test assertion.

7. **Configurable search weights from day one** — FTS vs semantic weights environment-driven, tunable without redeployment.

## Challenges

1. **E2E validation still infrastructure-gated — fourth consecutive epic.** Ollama cluster-only, Keycloak cluster-only. Story 6.2 validated with stored embeddings. Story 6.3 couldn't do full auth E2E locally.

2. **`test-pipeline.sh` not extended for search.** Epic 6 shipped 4 stories, a new API endpoint, and a frontend page — none covered by the smoke test. Regression gap.

3. **Pre-anonymization embeddings remain an FR28 gap.** Semantic search matches on pre-anonymization content. FTS correctly uses post-anonymization. Known limitation, not a defect. Needs dedicated story if FR28 interpreted strictly for semantic path.

4. **Story 6.1 E2E validation was manual state mutation.** Not the full import → embed → staging → approve flow. Subsequent stories did better with curl-based validation.

5. **Epic status bookkeeping gap** — `epic-6` remained `in-progress` despite all stories being `done`.

6. **Deploy failures discovered at deploy time, not before.** Historical pattern: `drizzle-kit push` dropping tables, lockfile drift, migration runner failures, missing roster user. All fixed reactively.

## Shebi's Input (Project Lead)

**Core concern:** Confidence in cumulative regression quality across all epics.

- "I want to make sure the application is well integrated at all layers, including regression from everything developed so far"
- "I have found issues when running `deploy.sh` and need to correct that — this should not happen anymore"
- "Don't start new development on a new epic until we have done all the review from the actual epic we are currently working on"
- When asked about confidence in the test suite: **"I am not confident"**

This is the defining feedback of this retrospective. The project lead is not confident in the quality gates. All action items flow from addressing this.

## Key Insights

1. **Per-story quality is high; systemic integration quality is low.** Every story gets code reviewed, unit tested, and E2E validated. But the cumulative system is not tested as a whole.

2. **The smoke test is a powerful tool that hasn't kept pace.** `test-pipeline.sh` covers Epics 1-5 well but was not updated for Epic 6. Two epics of features without smoke test coverage.

3. **No pre-deploy validation exists.** `deploy.sh` goes straight to image build without running tests. Failures are discovered after images are pushed.

4. **Epic boundaries need to be hard gates.** Without structural enforcement, the team naturally bleeds forward into the next epic before the current one is verified.

5. **The team fixes things — but reactively.** Every deploy failure was fixed. But the same class of failure recurs because there's no prevention mechanism.
